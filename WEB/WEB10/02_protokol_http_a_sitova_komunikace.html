Princip protokolu

Bezstavovost (Stateless) & Struktura zprávy

Proč si server nepamatuje předchozí dotazy a jak se udržuje stav přihlášení

http • surový požadavek a odpověď 
/* 1. HTTP REQUEST (Klient → Server) */
GET /api/student-profile HTTP/1.1
Host: edu-portal.cz
User-Agent: Mozilla/5.0 (Windows NT 10.0)
Cookie: session_id=a9f8e7c6b5
Accept: application/json

/* 2. HTTP RESPONSE (Server → Klient) */
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 42

{"student": "Jan Novák", "ročník": 3}

Proč je HTTP bezstavové (Stateless)?

Každý HTTP dotaz je pro server zcela izolovanou transakcí. Server si mezi požadavky neudržuje žádné kontextové spojení v paměti, což umožňuje obrovské horizontální škálování na miliony uživatelů.

Jak se řeší stav (Přihlášení, Košík)?

  • HTTP Cookies: Server pošle hlavičku Set-Cookie: sid=xyz; HttpOnly; Secure. Prohlížeč tuto hodnotu automaticky přikládá do každého dalšího požadavku.
  • Tokeny (JWT / Bearer): Předávání v hlavičce Authorization: Bearer [token].
  • Session na serveru: Data relace jsou uložena v Redis/databázi serveru pod ID z cookie.
Evoluce standardu

HTTP/1.1 vs. HTTP/2: Konec zpoždění

Přechod od textového protokolu k binárnímu multiplexování

Problémy HTTP/1.1 (1999)

  • Head-of-line Blocking: V jednom TCP spojení musely požadavky čekat ve frontě (FIFO). Pokud se první obrázek stahoval pomalu, zablokoval všechny ostatní.
  • Omezení prohlížečů: Prohlížeč mohl na jednu doménu otevřít max. 6 paralelních TCP spojení naráz.
  • Nezbytné obezličky (Antipatterns): Spojování ikon do sprite obrázků, spojování CSS do jednoho obřího souboru, doménový sharding (rozsekání na subdomény).

Revoluce HTTP/2 (2015)

  • Binární protokol: Místo čistého textu jsou data dělena na přesné binární rámce (Frames).
  • Multiplexing: Stovky nezávislých požadavků a odpovědí probíhají současně uvnitř jediného TCP spojení. Žádné zdržování fronty.
  • Komprese hlaviček (HPACK): Eliminace redundance – hlavičky jako User-Agent a Cookie se neposílají pokaždé znovu v plné délce.
  • Prioritizace proudů: Prohlížeč může určit, že CSS a písma mají přednost před obrázky.
Současnost a budoucnost

HTTP/3: Proč opustit TCP a přejít na QUIC?

Řešení ztráty paketů v mobilních sítích a zrychlení navazování spojení (0-RTT)

1. Limitace TCP

Protože HTTP/2 běží nad jediným TCP spojením, ztráta jediného síťového paketu způsobí, že operační systém pozastaví všechny multiplexované streamy, dokud ztracený paket znovu nedorazí.

2. Protokol QUIC nad UDP

HTTP/3 opouští pomalé TCP jádro v OS a přechází na protokol QUIC (vyvinutý Googlem), který běží nad rychlým protokolem UDP. Ztráta paketu v jednom streamu neovlivní žádný jiný proud!

3. Bleskový start (0-RTT)

V HTTP/3 jsou transportní spojení a šifrování TLS 1.3 sloučeny do jednoho kroku. Opakované návštěvy webu mohou posílat data okamžitě s nulovou latencí (0-RTT Handshake).

Co musíte bezpečně ovládat z okruhu č. 2 (Protokol HTTP)

Okruh absolutoria č. 2

1. Bezstavovost protokolu

Každý dotaz je nezávislý. Stav uživatele je udržován na aplikační úrovni pomocí HTTP cookies a relací (sessions).

2. Formát HTTP zprávy

Řádek požadavku/odpovědi (Metoda/Kód), hlavičky klíč-hodnota, prázdný řádek CRLF a volitelné tělo (Body).

3. Rozdíl HTTP/1.1 vs HTTP/2

HTTP/1.1 posílá text po jednom požadavku v TCP. HTTP/2 je binární a multiplexuje stovky proudů v jednom TCP spojení.

4. Význam HTTP/3 (QUIC)

Běží nad protokolem UDP. Eliminuje zdržení při ztrátě paketů v mobilních sítích a integruje TLS 1.3.

Typická otázka u absolutoria

„Proč u protokolu HTTP/2 již nemá smysl spojovat malé ikonky do CSS spritů nebo slučovat všechny JS skripty do jednoho obřího souboru?“
Správná odpověď: CSS sprity a slučování souborů byly obezličkou pro HTTP/1.1, aby se obešel limit 6 TCP spojení na doménu. V HTTP/2 probíhá stahování stovek malých souborů paralelně v jediném spojení s nulovým zpožděním. Oddělené menší soubory se navíc mnohem lépe cachují v prohlížeči při drobných aktualizacích webu.
