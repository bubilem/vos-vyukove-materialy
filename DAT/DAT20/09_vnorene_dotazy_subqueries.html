Skalární poddotazy

Skalární poddotazy v klauzuli WHERE

Poddotaz vracející právě jednu hodnotu (1 řádek, 1 sloupec)

Produkty s nadprůměrnou cenou 
SELECT 
  `id`, `name`, `price`
FROM `product`
WHERE `price` > (
  -- Vnitřní skalární dotaz vrátí průměr: 9 444,50 Kč
  SELECT AVG(`price`) 
  FROM `product` 
  WHERE `active` = TRUE
)
ORDER BY `price` DESC;

Jak se dotaz zpracuje?

  1. Databáze nejprve samostatně spočítá vnitřní dotaz v závorce: SELECT AVG(price)....
  2. Tento vnitřní dotaz vrátí jediné skalární číslo (např. 9444.50).
  3. Vnější dotaz se přetvoří na: WHERE price > 9444.50.
Chyba: Subquery returns more than 1 row
Pokud pro běžné porovnání (=, >, <) použijete poddotaz, který vrátí více než jeden řádek, dotaz okamžitě zhavaruje s chybou. Pro vícenásobné hodnoty musíte použít operátor IN, ANY nebo ALL!
Množinové poddotazy

Operátory IN, ANY a ALL

Porovnání hodnoty se sadou vrácených výsledků

Otázka u zkoušky
Operátory v praxi nad edu_eshop 
-- 1. Operátor IN: Zákazníci, kteří již nakoupili
SELECT `id`, `email` FROM `customer`
WHERE `id` IN (
  SELECT DISTINCT `customer_id` FROM `orders`
);

-- 2. Operátor > ALL: Dražší než VŠECHNO příslušenství
SELECT `name`, `price` FROM `product`
WHERE `price` > ALL (
  SELECT p.`price`
  FROM `product` p
  JOIN `product_category` pc ON p.`id` = pc.`product_id`
  WHERE pc.`category_id` = 4 -- ID kategorie Příslušenství
);

Rozdíl mezi ANY a ALL

  • x > ANY (...): Hodnota x musí být větší než alespoň jedna hodnota z poddotazu (ekvivalentní k: x > MIN(...)).
  • x > ALL (...): Hodnota x musí být větší než úplně všechny hodnoty ze sady (ekvivalentní k: x > MAX(...)).
  • x = ANY (...): Přesné synonymum pro operátor x IN (...).
Typy poddotazů

Korelované vs. Nekorelované poddotazy

Závislost vnitřního dotazu na řádcích vnějšího dotazu

Výkonnostní rozdíl

Nekorelovaný poddotaz

Je zcela nezávislý na vnějším dotazu. Lze jej vzít a spustit samostatně.

  • Provede se pouze 1× pro celý dotaz.
  • Výsledek se uloží do dočasné paměti a opakovaně používá.
  • Vysoký výpočetní výkon.

Korelovaný poddotaz

Uvnitř poddotazu se odkazujeme na sloupec z vnějšího dotazu (např. outer_p.id).

  • Vyhodnocuje se pro KAŽDÝ řádek vnějšího dotazu znovu!
  • Má-li vnější tabulka 10 000 řádků, vnitřní dotaz se spustí 10 000×!
  • Může způsobit dramatické zpomalení (často lze lépe nahradit pomocí JOIN).
Korelovaný poddotaz (Pomalé: běh N×) 
SELECT c.`email`, o1.`id`, o1.`created_at`, o1.`total_price`
FROM `customer` c
JOIN `orders` o1 ON c.`id` = o1.`customer_id`
WHERE o1.`created_at` = (
  -- Spustí se znovu pro KAŽDÝ řádek vnějšího dotazu (N-krát)!
  SELECT MAX(o2.`created_at`)
  FROM `orders` o2
  WHERE o2.`customer_id` = c.`id`
);
Optimalizace přes JOIN (Rychlé: běh 1×) 
SELECT c.`email`, o.`id`, o.`created_at`, o.`total_price`
FROM `customer` c
-- 1. Odvozená tabulka: agregace se spočte pouze 1×
JOIN (
  SELECT `customer_id`, MAX(`created_at`) AS `max_date`
  FROM `orders`
  GROUP BY `customer_id`
) latest ON latest.`customer_id` = c.`id`
-- 2. Efektivní indexové spojení na nalezenou objednávku
JOIN `orders` o ON o.`customer_id` = latest.`customer_id`
               AND o.`created_at` = latest.`max_date`;
Existenční testy & Anti-Join

Predikáty EXISTS a NOT EXISTS

Bleskové ověření existence (Short-Circuit) vs. Anti-Join techniky (LEFT JOIN / HAVING)

Otázka k absolutoriu
1. NOT EXISTS (Doporučeno: Short-Circuit) 
SELECT c.`id`, c.`email`
FROM `customer` c
WHERE NOT EXISTS (
  SELECT 1 FROM `orders` o 
  WHERE o.`customer_id` = c.`id`
);
2. Klasický Anti-Join: LEFT JOIN + WHERE IS NULL 
SELECT c.`id`, c.`email`
FROM `customer` c
LEFT JOIN `orders` o ON c.`id` = o.`customer_id`
WHERE o.`customer_id` IS NULL;
3. Agregační varianta: GROUP BY + HAVING 
SELECT c.`id`, c.`email`
FROM `customer` c
LEFT JOIN `orders` o ON c.`id` = o.`customer_id`
GROUP BY c.`id`, c.`email`
HAVING COUNT(o.`id`) = 0; -- resp. HAVING o.`customer_id` IS NULL
Metoda Mechanika vyhodnocení Režie a výkon
1. NOT EXISTS Short-circuit (končí u 1. nalezené objednávky) Minimální (O(1) na řádek)
2. LEFT JOIN + WHERE Anti-join filtr optimalizovaný jádrem DB Minimální (žádné řazení)
3. GROUP BY + HAVING Full Join + Temporary Table + Sort v paměti Vysoká (zbytečná agregace)

Proč je varianta s GROUP BY + HAVING neefektivní?

  • Plný průchod všech řádků: Má-li zákazník 1 000 objednávek, NOT EXISTS skončí okamžitě po nalezení první. GROUP BY musí načíst a agregovat všech 1 000 záznamů!
  • Dočasná tabulka a řazení: Seskupování vyžaduje režii Using temporary; Using filesort, což u velkých tabulek prudce zvyšuje zátěž RAM a disku.
  • Sémantika WHERE vs. HAVING: WHERE eliminuje záznamy před jakýmkoliv seskupením, kdežto HAVING až po kompletní agregaci – zbytečně agregujete miliony řádků, které vzápětí zahodíte.
  • Režim ONLY_FULL_GROUP_BY: V moderním SQL standardu vyžaduje HAVING agregační funkci (např. COUNT(o.id) = 0), nekumulovaný sloupec v HAVING způsobí chybu.
Rekapitulace & Zkouška

Shrnutí: Vnořené dotazy a optimalizace

Rozhodovací matice technik, výkonnostní pravidla a příprava na absolutorium

Okruh absolutoria č. 14
1

Skalární poddotazy ve WHERE

Kdy použít: Porovnání atributu s agregovanou hodnotou celku (např. price > (SELECT AVG(price)...)).
Zlaté pravidlo: Musí vracet striktně 1 řádek a 1 sloupec, jinak dotaz havaruje s chybou Subquery returns more than 1 row.

2

Množinové predikáty (IN, ANY, ALL)

Kdy použít: Ověřování hodnoty vůči dynamickému seznamu z vnitřního dotazu (např. ID kategorií).
Kritické úskalí: Pozor na NOT IN a NULL! Obsahuje-li poddotaz jediné NULL, vrátí prázdnou sadu. Pro bezpečný test volte NOT EXISTS.

3

Korelované dotazy vs. JOIN optimalizace

Mechanika: Nekorelovaný dotaz běží pouze 1×. Korelovaný se spouští pro každý řádek znovu (N-krát, O(N × M)).
Optimalizace: Místo pomalého poddotazu ve WHERE použijte JOIN s odvozenou tabulkou (GROUP BY), kde agregace proběhne pouze 1×.

4

Existenční testy & Anti-Join (EXISTS vs. LEFT JOIN)

Short-circuit: EXISTS končí okamžitě po nalezení prvního záznamu v indexu – neprochází celou tabulku.
Anti-Join pravidlo: Pro záznamy bez vazby volte NOT EXISTS nebo LEFT JOIN ... WHERE IS NULL. Vyhněte se zbytečnému GROUP BY + HAVING!

Zkušební otázka k absolutoriu (Okruh č. 14 – Vnořené dotazy a optimalizace):

„Vysvětlete rozdíl mezi korelovaným a nekorelovaným poddotazem z hlediska vykonávání databázovým strojem. Proč je pro hledání entit bez vazby predikát NOT EXISTS dramaticky rychlejší než konstrukce s GROUP BY a HAVING?“

Klíč k odpovědi: 1) Nekorelovaný dotaz je nezávislý na vnějších datech, vyhodnotí se pouze 1× a výsledek se nacachuje. 2) Korelovaný dotaz odkazuje na sloupce vnějšího dotazu (např. c.id), proto se musí spouštět znovu pro každý řádek zvlášť (N-krát) – optimalizuje se přepisem na JOIN s odvozenou tabulkou. 3) NOT EXISTS využívá short-circuit (zastaví se u 1. nalezeného záznamu v indexu). Naproti tomu GROUP BY + HAVING musí pospojovat a seskupit všechny záznamy v paměti (s režijní dočasnou tabulkou a filesortem) a teprve poté zahodí většinu výsledků.
